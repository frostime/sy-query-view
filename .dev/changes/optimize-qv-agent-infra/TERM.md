## 语义对齐（任务核心）

你最早说的三个东西要互相对齐：**函数实际做的**、**显式标注的类型**、**写了注释的文档**。
本任务的靶子就是"当前它们对不上的地方"（例如打印出来 `Block[]`、实际返回带工具箱的包裹列表）。
注意区分：**源码内部就不一致**（类型 vs 实现）属于 N6 修的；**文档与源码脱节**（手工写的参考文档过时）属于生成器解决的。两者都算"不对齐"，但成因和手段不同，不要混为一谈。

## 第 1 层与第 2 层

- **第 1 层 = 本轮任务（本 graph）**：这一轮 end-to-end 结束时，尽量不再有已知不对齐。
- **第 2 层 = 长期规范**：让"后续写代码的人/协作流程"持续保持对齐的机制（AGENTS.md、SKILL 之类），是独立的长期基础设施问题，只在本任务中预订入口，不做细节。

## 参考文档（旧称 agent-ref）

给 AI 写代码时查的 API 说明书。v1.3 是手工写的（`docs/en_US/agent-ref/`），出了名的会过时；本任务要把它的来源换成生成器。产物形态未最终定（md / d.ts 都可能，用户已定"形式无所谓、高保真优先"）。

## 生成器

从源码自动产出"参考文档"的程序：抠签名（类型检查器/tsc 声明）、抠注释（JSDoc 解析）、算别名（注册调用点）。**它不编造知识、不评判对错——只照搬"源码当前长什么样"**。注意它不担保正确，正确性由结项复核兜底。

## 注册调用点

代码里 `this.register(this.X, { aliases: [...] })` 和 `addAlias(Query, 'x', [...])` 这种调用。运行时动态注册的方法名/别名，静态声明里没有；但**调用点本身是静态代码**，生成器可以解析它算出完整名字集合（已实测：DataView 19 处调用 → 171 个名字）。这是动态 API 的"真相源"。

## 结项复核（我原先误称"行为测试/测试"）

你的定义：**本轮结尾阶段**（如 N6 时）派 subagent 复核一遍，或写可长期复用的检测脚本。原则现在定：生成物与运行时对齐要有一个验证手段；但**细节（测什么、脚本怎么写）不在开局敲死**。节点可预订、后置处理。

## wrapped 列表（包裹列表）

`wrapList()` 返回的带 `.pick()/.groupby()/.addcols()` 等附加工具的数组（`IWrappedList`）。多处"声明写了 `Block[]`、实际返回 wrapped"的不对齐都由它引起，因为 `wrapList` 的返回类型被 TS 推导成了普通数组。这是坑清单里最大的一族。
